你正在启动一个新需求工作流，使用plan模式完成phase 1的需求和方案设计，禁止有模糊的地方自加推测而不确认。

**立即按顺序执行，确认前不写入任何文件。**

## Phase 1a — 需求澄清

1. 判断需求描述是否存在歧义：
   
   - **有歧义** → 列出 2~4 个关键问题（功能边界、验收标准、约束条件），**等待主公明确**后继续
   - **足够清晰** → 跳过直接进入下一步

2. 在对话中编写 `requirements.md` 内容（**不写入文件**）：
   
   - **功能目标**：描述该功能的核心目标和作用
   - **功能边界**：明确做什么/不做什么
   - **验收标准**：可测试的条件列表（每条能被明确判断通过或失败）
   - **约束条件**：技术限制、性能要求、依赖关系等

## Phase 1b — 技术设计

3. 理解相关代码和上下文后，在对话中编写 `design.md` 内容（**不写入文件**）：
   
   - **技术方案**：描述实现方案和核心逻辑，非特殊要求不要写完整代码实现，涉及 UI 用 ASCII 草图
   - **涉及文件**：列出需要新建或修改的文件
   - **TODO List**：`- [ ]` 格式，任务复杂度高可以考虑拆分为更小粒度的可执行子任务
   - **决策记录**：记录关键技术选型及原因

## 一次性确认（在此等待主公）

4. 展示最终的todo list，请主公**一并确认**最终任务
5. **主公批准后**，执行以下所有写入操作：
   * 根据需求描述生成英文 kebab-case 功能名（2~4 个单词，如 `user-auth`、`order-export`），告知主公
   * 执行 `git checkout -b feature/[功能名]`
   - 创建目录 `docs/tech/[功能名]/`
   - 写入 `docs/tech/[功能名]/requirements.md`
   - 写入 `docs/tech/[功能名]/design.md`
   - 更新 `docs/tech/index.md`，添加本次功能条目（不存在则创建）
6. 告知主公写入完成，然后立即使用 Skill 工具调用 `auto-coding` skill，自动进入开发+测试阶段
